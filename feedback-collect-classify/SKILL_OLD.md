# 用户反馈收集与分类

## 目标多维表格配置

本技能支持用户实时配置目标多维表格，执行时会先询问用户以下信息：

- **Base URL 或 Base Token**: 目标多维表格的链接或base_token
- **Table Token 或 Table Name**: 目标数据表的token或名称
- **字段映射**: 表格字段与标准字段的对应关系
- **图片字段**: 用于存储反馈图片的字段名称（如果有）

写入时使用 `--as user` 身份执行 `lark-cli base +record-batch-create`

## 默认字段映射

如果用户未提供自定义字段映射，使用以下标准字段顺序：

- `SourceID`: 消息唯一标识
- `来自群聊`: 群聊名称
- `反馈原文`: 原始消息文本
- `反馈入口`: 固定填写"群聊"
- `问题分类`: 技术问题/使用咨询/待划定
- `反馈人`: 消息发送者
- `回复内容`: 群聊回复文本
- `回答人`: 回复者姓名
- `反馈时间`: 消息发送时间
- `standard_title`: 标准化标题
- `是否命中知识库`: 是/否/空字符串
- `跟进状态`: 待跟进/已完成/重复问题
- `反馈图片`: 图片URL或附件token（如果支持）

## 何时使用

用户需要你：

- 扫描群聊消息，收集用户反馈
- 判断哪些消息值得进入反馈表
- 对反馈做三大分类：`技术问题` / `使用咨询` / `待划定`
- 为后续问题池、FAQ 检索和知识沉淀生成标准化标题与描述
- 先做“收集与分类”，暂时不做负责人分派、问题归并或知识条目撰写
- 输出字段顺序与多维表格“反馈记录”表严格对齐，便于直接写入飞书多维表格


## 默认数据来源

默认直接拉取群聊记录，不要优先要求用户手动复制粘贴聊天内容。

常规流程只有两步：

1. 确认目标群和时间窗口
2. 拉取群聊记录后进入收集、标准化与分类流程

只有在群聊记录确实无法读取时，才退回手动文本输入。

## 时间窗口调度规则

执行此技能时，必须按以下规则确定数据拉取的时间窗口，不得让用户手动指定日期：

- **周一执行**：拉取 **上周五**（周一前最近一个工作日）00:00 ~ 23:59 的消息
- **周二 ~ 周五执行**：拉取 **前一天** 00:00 ~ 23:59 的消息
- **周六、周日不执行**：如果用户请求在周六或周日运行此流程，应告知用户该流程仅在周一至周五执行，跳过本次运行

调度规则示例（假设当前日期为 2026-08-03 周一）：

| 执行日 | 拉取时间窗口 |
|--------|-------------|
| 周一 | 上周五（如 2026-07-31） |
| 周二 | 周一（如 2026-08-04→拉取 2026-08-03） |
| 周三 | 周二 |
| 周四 | 周三 |
| 周五 | 周四 |
| 周六 | 不执行 |
| 周日 | 不执行 |

注意：周一拉取上周五而非上周日，因为周六日不产生消息，且周一拉取的是距当前最近一个工作日的消息。

## 群聊读取方式

如果用户给的是群名，先查群：

```bash
lark-cli im +chat-search --query "<群名关键词>" --as user --json
```

拿到 `chat_id` 后，按时间窗口拉消息：

```bash
lark-cli im +chat-messages-list --chat-id "<chat_id>" --as user --start "<start_iso>" --end "<end_iso>" --order asc --page-size 200 --json
```

如果需要补充“回复某人”“还是不行”“这个问题”的上下文，可继续：

- 读取相邻时间段消息
- 或按 thread/message 补抓上下文

如果平台拿到的是原始飞书消息结构，先整理成下面的统一结构再处理：

```json
{
  "group_name": "本地版答疑群",
  "time_window": "2026-07-01 00:00 to 2026-07-07 23:59 Asia/Shanghai",
  "messages": [
    {
      "message_id": "optional",
      "message_time": "2026-07-01 10:15",
      "sender": "张三",
      "text": "昨天还能正常使用 lark-cli，今天就报错了",
      "reply_to": "optional",
      "thread_id": "optional"
    }
  ]
}
```

## 知识库读取规则
如果任务要求判断"是否命中知识库"，处理原则如下：

- 仅当用户明确指定了知识库文档时，才进行知识库命中判断
- 仅对 `技术问题` 和 `使用咨询` 两个分类判断是否命中知识库
- 命中标准是"知识库中已���在语义等价或同类标准问题，且答案稳定"
- 若知识库读取失败、权限不足或信息不足，不要硬判为命中；此时填 `否`，并将 `问题分类` 设为 `待划定`
- 如果用户未指定知识库文档，`是否命中知识库` 字段填空字符串 `""`



## 工作流

### 1. 先拉消息，再做收集

先确认时间窗口和目标群，再读取消息。

建议默认窗口：

- 用户说“最近一周”时，读取最近 7 个自然日
- 用户说“今天”时，只读取当天消息
- 用户未指定时，默认最近 24 小时

拉完消息后，不要默认每条消息都是反馈。

### 2. 做收集判断

只收集以下内容：

- 明确提问
- 明确报错
- 对已有问题补充了新信息

不收集以下内容：

- 明确产品建议（不录入反馈表）

默认不收集以下内容：

- 公告
- 群管理动作
- 回复动作本身，如“试一下重装”
- 单纯附和，如“+1”
- 纯情绪表达
- 闲聊
- 信息不足且上下文无法补足

对不收集的内容，直接忽略，无需单独输出。

### 3. 给短句补上下文

如果消息本身过短，或明显依赖前文，先补 `context_summary`，再分类。

重点处理这类消息：

- “还是不行”
- “这个怎么处理”
- “能不能修复一下”
- “这是啥问题”
- “+1 同样报错”
- 以“回复某人”开头

补法：

1. 向前看同线程或同时间段最近 3 到 5 条消息
2. 找到最近一个完整问题描述
3. 用一句话总结上下文，写入 `context_summary`

如果补完仍无法判断，直接归为 `待划定`。

### 4. 先标准化问题

对每条被收集的反馈，都先输出：

- `standard_title`
  一句简洁、可复用、可去重的标题

要求：

- 不要照抄原话
- 不要带情绪
- 标题尽量面向“后续归并”
- 先把原始表达改写成适合入表的标准化表述，再进入分类判断


### 5. 问题分类

`问题分类` 只能使用以下三个值：

- `技术问题`
- `使用咨询`
- `待划定`

定义如下：

- `技术问题`
  本应可用，但实际异常、报错、失效、结果错误、卡死、白屏、兼容失败、数据丢失。（对应原 BUG）
- `使用咨询`
  用户在问怎么用、当前能力边界是什么、权限怎么申请、收费怎么理解、入口在哪、规则是什么。（对应原 使用问题）
- `待划定`
  当前信息不足、语义含混、上下文补全后仍无法稳定归类，或内部置信度低于 70。

**注意：产品建议不录入反馈表，收集时直接过滤掉。**

### 6. 置信度评估

对每条被收集的反馈，评估 `confidence_score`，范围为 0 到 100 的整数。

建议口径：

- `90-100`：信息明确，分类无明显歧义
- `80-89`：有上下文支撑，分类较稳定
- `70-79`：基本可判断，但仍有轻微歧义
- `60-69`：信息不足，分类不稳定
- `<60`：严重缺少信息，需要人工复核

判定规则：

- `confidence_score < 70` 时，`问题分类` 直接填 `待划定`
- `confidence_score < 70` 时，直接归为 `待划定`

### 7. 标记是否命中知识库

`是否命中知识库` 字段规则：

- 仅对 `技术问题` 和 `使用咨询` 两个分类判断是否命中知识库
- 如果知识库中已存在语义等价或同类标准问题，且答案稳定，填 `是`
- 如果知识库中不存在对应条目，填 `否`
- 如果知识库读取失败、权限不足或信息不足，填 `否`，并将 `问题分类` 设为 `待划定`
- `产品建议` 和 `待划定` 分类不填写此字段，保持���字符串 `""`

### 8. 识别重复问题

对每条被收集的反馈，与表中已有记录（特别是最近 30 天内的记录）进行语义比对，判断是否为重复问题。

**重复问题判定标准：**

- 与已有记录的 `standard_title` 语义等价（描述的是同一个问题或诉求）
- 与已有记录的 `反馈原文` 核心诉求一致
- 即使措辞不同，但本质是同一类问题（如"网络连接断开"和"频繁提示网络已断开"）

**标记规则：**

- 判定为重复问题时，`跟进状态` 标记为 `重复问题`
- 同时将 `回答人` 和 `回复内容` 设为空字符串 `""`（因为该问题已有原始记录跟进）
- 非重复问题按原有规则标记 `待跟进` 或 `已完成`

### 9. 输出格式

输出严格 JSON，不要输出解释性段落。

输出结构如下（字段顺序与多维表格"反馈记录"表一致）：

```json
{
  "window_summary": {
    "group_name": "",
    "time_window": "",
    "total_messages": 0,
    "collected_count": 0
  },
  "dimension_summary": {
    "技术问题": 0,
    "使用咨询": 0,
    "待划定": 0
  },
  "collected_items": [
    {
      "反馈时间": "",
      "standard_title": "",
      "反馈人": "",
      "反馈内容": "",
      "问题分类": "",
      "回答人": "",
      "回复内容": "",
      "跟进状态": "",
      "来自群聊": "",
      "是否命中知识库": "",
      "反馈入口": ""
    }
  ]
}
```

字段规则（按输出顺序排列）：

- `反馈时间`
  datetime 类型，格式为 `yyyy/MM/dd HH:mm`，取消息发送时间
- `standard_title`
  标准化后的问题标题，用于后续归并、去重和知识库检索
- `反馈人`
  user 类型（多选），取消息发送者名称，如果是匿名则用"匿名用户"
- `反馈内容`
  原始消息文本
- `问题分类`
  只允许 `技术问题` / `使用咨询` / `待划定`
- `回答人`
  user 类型（多选），当 `跟进状态` 为 `已完成` 时填写回答者姓名；`待跟进` 或 `重复问题` 时为空字符串
- `回复内容`
  群聊中对反馈的回复文本；当 `跟进状态` 为 `待跟进` 或 `重复问题` 时填空字符串
- `跟进状态`
  只允许 `待跟进` / `已完成` / `重复问题`；有回复则已完成，无回复则待跟进，与已有记录问题重复则标记为重复问题
- `来自群聊`
  select 类型，固定选项：`NIO Chat用户社群` / `本地版答疑群`。根据读取的群名填写对应值
- `是否命中知识库`
  仅当 `问题分类` 为 `技术问题` 或 `使用咨询` 时填写 `是` 或 `否`；其他分类为空字符串 `""`
- `反馈入口`
  固定填写 `群聊`，标记该反馈的来源入口

## 强约束

最终输出必须严格遵守以下约束，任何违反均视为格式错误：

1. **输出格式**：最终输出必须是一个且仅一个 JSON 对象，不得包含任何 Markdown、表格、说明文字、代码块、列表或注释。
2. **顶层字段完整性**：顶层必须包含且仅包含 `window_summary`、`dimension_summary`、`collected_items` 三个字段，不得增删字段。
3. **记录字段完整性**：`collected_items` 中的每一项都必须包含全部字段，字段名必须与输出格式中定义的完全一致（包括大小写和命名风格）。
4. **空值处理**：即使某字段暂无值，也必须保留该字段并填空字符串 `""`、数字 `0`、布尔值 `false` 或空数组 `[]`，不得省略字段。
5. **分类约束**：`问题分类` 只允许 `技术问题` / `使用咨询` / `待划定` 三个值，不得出现其他值，也不得为空字符串。
6. **跟进状态约束**：`跟进状态` 只允许 `待跟进` / `已完成` / `重复问题` 三个值，不得为空字符串。
7. **回复字段一致性约束**：
   - 当 `跟进状态` 为 `待跟进` 或 `重复问题` 时，`回答人` 和 `回复内容` 必须为空字符串 `""`
   - 当 `跟进状态` 为 `已完成` 时，`回答人` 和 `回复内容` 不得同时为空
8. **知识库字段约束**：`是否命中知识库` 仅当 `问题分类` 为 `技术问题` 或 `使用咨询` 时填写 `是` 或 `否`；其他分类必须填空字符串 `""`。
9. **待划定约束**：
   - 当信息不足、上下文无法补足、知识库判断失败或无法稳定分类时，`问题分类` 必须为 `待划定`
10. **统计一致性约束**：
   - `dimension_summary` 三类计数之和必须等于 `window_summary.collected_count`
   - `collected_items` 数量必须等于 `window_summary.collected_count`
   - `window_summary.collected_count` 不得大于 `window_summary.total_messages`
11. **字段数量约束**：`collected_items` 中每条记录只保留 12 个字段，不得额外增加字段。
12. **校验规则**：输出前必须逐项校验以上所有约束。若输出缺少任一字段、任一字段值不合法或任一约束不满足，必须先修正再输出，不得将格式错误的 JSON 发送给用户。

## 使用模板

把下面这段作为本技能的工作提示：

```text
请先主动读取群聊记录，再完成“收集 + 分类”。

当前时间窗口：{{time_window}}
群名：{{group_name}}

要求：
1. 如果用户给的是群名，先定位 chat_id，再按时间窗口拉消息
2. 对读取到的消息先做候选反馈收集
3. 先对收集到的反馈生成 `standard_title`
4. 再基于标准化后的问题做三大分类（技术问题/使用咨询/待划定），过滤掉产品建议
5. 对依赖前文的短句补充 context_summary
6. 如果任务要求判断知识库命中，先读取知识库外链，再判断是否命中
7. 无法稳定判断的问题直接归为 `待划定`
8. 最终输出前必须校验顶层字段、记录字段、枚举值、统计汇总和空值规则
9. 最终主表每条记录只保留 12 个字段，字段顺序与多维表格“反馈记录”表严格对齐，不要额外加列
10. 只输出严格 JSON，不要输出解释性文字
```

## 边界提醒

- 不要把公告、附和、纯闲聊塞进 `collected_items`
- 不要把“回复动作”误当成新问题
- 不要把“不会用”和“产品坏了”混成一类
- 不要默认要求用户粘贴消息内容，优先自动读取群聊
- 不要在本技能中做负责人分配
- 不要在本技能中做问题归并
- 不要在本技能中直接生成知识条目
- 不要把产品建议录入反馈表，收集时直接过滤掉
