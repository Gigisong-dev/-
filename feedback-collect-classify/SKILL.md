# 用户反馈收集与分类

`feedback-collect-classify` 从飞书群聊消息流中主动拉取消息，筛选有效反馈，补足上下文，按分类标准输出结构化 JSON，并可写入飞书多维表格（Bitable）。

## 触发与不触发边界

**Use when:**
- 用户想从飞书/Lark 群聊收集用户反馈并分类（技术问题/产品建议/使用咨询/待划定，或用户自定义分类）
- 反馈表初始化、周期性（每日/工作日）反馈收集、后续问题池归并前的数据整理

**Do NOT use for:**
- 非飞书群聊来源的反馈（微信、钉钉等）
- 一次性临时任务、与收集分类无关的问答
- 在群聊中直接回复/处理用户问题（那是答疑流程，不是收集）
- 直接生成知识库条目或文档
- 负责人分配、问题归并合并分析

## 前置条件（Prerequisites）

执行本技能前必须满足以下条件，任一不满足则先向用户确认或停止：

1. **lark-cli 已安装**：本技能依赖 `lark-cli` CLI 工具（消息拉取、图片下载/上传、多维表格写入）。
   - 检查：`lark-cli --version`；未安装时提示用户先安装并完成配置，不继续执行。
2. **Lark 身份认证完成**：所有操作用 `--as user` 身份执行；若提示认证/授权，先引导用户完成。
3. **多维表格访问权限**：用户对目标 Base 具备写权限（`lark-cli base +record-list ...` 可读记录）。
4. **群聊访问权限**：用户是目标群成员（`lark-cli im +chat-search ...` 可搜到目标群）。
5. **（可选）云空间上传权限**：开启图片处理时，用户需具备目标文件夹上传权限。
## 目标多维表格配置

执行时会先询问用户以下信息：

- **Base URL 或 Base Token**：目标多维表格的链接或 base_token
- **Table Token 或 Table Name**：目标数据表的 token 或名称
- **字段映射**：表格字段与标准字段的对应关系（默认映射见下）
- **图片字段**：用于存储反馈图片的字段名称（如果有）

写入时使用 `--as user` 身份执行 `lark-cli base +record-batch-create`。

## 默认字段映射

未提供自定义映射时，按以下标准字段顺序写入（完整字段规则见 `references/field-mapping-guide.md`）：

- `提交时间` / `standard_title` / `反馈人` / `反馈原文` / `附件` / `一级分类` / `二级分类` / `跟进状态` / `回答人` / `回复内容` / `来自群聊` / `是否命中知识库`

`一级分类` 默认四值：`技术问题` / `产品建议` / `使用咨询` / `待划定`（用户提供具体分类时使用用户分类标准）。

## 时间窗口调度规则

- **自定义时间窗口**：用户指定具体时间范围
- **默认规则**（用户未指定时）：
  - 周一执行：拉取上周五（周一前最近一个工作日）00:00 ~ 23:59 消息
  - 周二 ~ 周五执行：拉取前一天 00:00 ~ 23:59 消息
  - 周六、周日：不执行；告知用户该流程仅在周一至周五执行，跳过本次运行

## 默认数据来源

默认直接拉取群聊记录，不要优先要求用户手动复制粘贴聊天内容。常规流程：

1. 确认目标表格、群聊和时间窗口
2. 拉取群聊记录后进入收集、标准化与分类流程
3. 处理消息中的图片内容
4. 写入目标多维表格

只有在群聊记录确实无法读取时，才退回手动文本输入。
## 群聊读取方式（命令骨架）

**输入**：群名或群链接 + 时间窗口
**输出**：统一结构的消息列表（原始飞书消息整理后的结构见 `references/message-structure.md`）

若给的是群名，先查群获取 `chat_id`：

```bash
lark-cli im +chat-search --query "<群名关键词>" --as user --json
```

按时间窗口拉消息：

```bash
lark-cli im +chat-messages-list --chat-id "<chat_id>" --as user --start "<start_iso>" --end "<end_iso>" --order asc --page-size 200 --json
```

上下文补抓（"回复某人""还是不行""这个问题"）：读取相邻时间段消息，或按 thread/message 补抓上下文。完整消息结构字段见 `references/message-structure.md`。

## 图片处理（命令骨架）

**输入**：消息中的 image_key / URL
**输出**：上传后的文件 token 或 URL，写入记录附件字段

```bash
# 下载图片到本地
lark-cli im +image-download --image-key "<image_key>" --output "/tmp/image.jpg" --as user

# 上传到云空间
lark-cli drive +file-upload --file "/tmp/image.jpg" --parent-folder-token "<folder_token>" --as user
```

图片字段类型（附件/URL/混合）、完整流程、错误处理见 `references/image-processing-guide.md`。

## 知识库读取规则

`是否命中知识库` 字段规则：

- **未提供知识库时**：不填充此字段，填空字符串 `""`，跳过知识库命中判断，且不影响 `一级分类` 判定。
- **提供知识库时**：仅对 `技术问题`、`产品建议`、`使用咨询` 三个分类判断命中；命中标准为"知识库已存在语义等价或同类标准问题，且答案稳定"。
- 知识库读取失败/权限不足/信息不足时：填 `否`，并将 `一级分类` 设为 `待划定`。
## 工作流（概览 → 各阶段输入/输出）

### 1. 配置确认阶段
**输入**：用户的收集请求（群名/群链接、时间窗口、目标表格、分类标准）
**输出**：完整配置（base_token、table_token、group_name、time_window、classification_standard、image_field_enabled、custom_field_mapping）

向用户确认：
- 目标多维表格信息（Base URL/Token + Table Token/Name）
- 是否需要自定义字段映射
- 分类标准（默认四分类，或用户自定义分类）
- 是否需要处理图片及图片字段配置
- 目标群聊信息（群名或群链接）
- 时间窗口（自定义或默认规则）

### 2. 消息拉取阶段
**输入**：`chat_id` + `time_window`
**输出**：原始消息列表（含文本、图片、reply_to、thread_id）

- 若给群名，先定位 chat_id
- 按时间窗口拉取消息（预期耗时见"耗时与超时"章节）
- 提取文本内容和图片信息

### 3. 收集判断阶段
**输入**：原始消息列表
**输出**：候选反馈消息子集

**只收集**：
- 明确提问 / 明确报错 / 对已有问题补充了新信息
- 明确产品建议（默认分类标准含 `产品建议` 时收集并录入；用户分类不含产品建议分类时按"不收集"处理）

**不收集**：公告、群管理动作、回复动作本身（如"试一下重装"）、单纯附和（"+1"）、纯情绪表达、闲聊、信息不足且上下文无法补足。不收集内容直接忽略，无需单独输出。

**注意：二级分类根据具体问题类型填写，可为空字符串**
### 4. 上下文补充阶段
**输入**：候选反馈中过短/依赖前文的消息 + 相邻时间段/同线程消息
**输出**：`context_summary`（一句话上下文总结）

重点处理："还是不行"、"这个怎么处理"、"能不能修复一下"、"这是啥问题"、"+1 同样报错"、以"回复某人"开头等。

补法：
1. 向前看同线程或同时间段最近 3 到 5 条消息
2. 找到最近一个完整问题描述
3. 用一句话总结上下文，写入 `context_summary`

如果补完仍无法判断，直接归为 `待划定`。

### 5. 标准化处理阶段
**输入**：候选反馈消息（含 context_summary）
**输出**：`standard_title`（标准化标题）

要求：不要照抄原话、不带情绪、面向"后续归并"、先改写成适合入表的标准化表述再进入分类判断。

### 6. 问题分类阶段
**输入**：标准化后的反馈
**输出**：`一级分类`（默认四分类或用户自定义分类）

**默认分类标准**：`技术问题` / `产品建议` / `使用咨询` / `待划定`，定义及判定标准见 `references/classification-rules.md`。

**用户自定义分类标准**：用户提供具体分类时，`一级分类` 只能使用用户定义的值，不再使用默认四分类。

**注意：默认分类标准下，产品建议需要录入反馈表；若用户分类标准中不含产品建议分类，则产品建议不录入反馈表，收集时直接过滤掉。**

### 7. 置信度评估阶段
**输入**：反馈消息 + 上下文
**输出**：`confidence_score`（0-100 整数）

口径：90-100 信息明确 / 80-89 有上下文支撑 / 70-79 轻微歧义 / 60-69 信息不足 / <60 需人工复核。`confidence_score < 70` 时 `一级分类` 直接填 `待划定`。详细口径见 `references/classification-rules.md`。
### 8. 知识库命中判断阶段
**输入**：`一级分类` + 用户是否提供知识库
**输出**：`是否命中知识库` 字段值

- 未提供知识库：不填充，空字符串 `""`，且不影响 `一级分类`
- 提供知识库时：仅对 `技术问题`/`产品建议`/`使用咨询` 判断 `是`/`否`；`待划定` 为空字符串 `""`
- 读取失败/权限不足/信息不足：填 `否` 并将一级分类设为 `待划定`

### 9. 图片处理阶段
**输入**：包含图片的反馈消息
**输出**：上传后的图片 token/URL，写入附件字段

1. 提取图片 image_key 和 URL
2. 下载图片到本地临时目录
3. 上传到用户指定的云空间文件夹
4. 获取文件 token 或 URL
5. 按配置的图片字段类型写入对应字段

失败处理：下载/上传失败按"重试与超时"章节执行；多次失败后记录错误信息到图片字段，不影响其他字段处理。

### 10. 重复问题识别阶段
**输入**：被收集反馈 + 表中已有记录（重点最近 30 天）
**输出**：重复标记（`跟进状态` = `重复问题` 或保持待跟进/已完成）

判定标准：与已有 `standard_title` 语义等价，或与 `反馈原文` 核心诉求一致，即使措辞不同但本质同类。标记为 `重复问题` 时，`回答人` 和 `回复内容` 设为空字符串 `""`。
### 11. 数据写入阶段 + Verify
**输入**：处理后的记录数组（字段映射 + 附件 + 分类）
**输出**：`lark-cli base +record-batch-create` 写入结果

```bash
lark-cli base +record-batch-create \
  --base-token "<base_token>" \
  --table-token "<table_token>" \
  --as user \
  --json << 'EOF'
{
  "records": [
    {
      "fields": {
        "提交时间": "2026/08/14 10:30",
        "standard_title": "标准化标题",
        "反馈人": ["张三"],
        "反馈原文": "问题描述",
        "附件": ["file_token_xxx"],
        "一级分类": "技术问题",
        "二级分类": "",
        "跟进状态": "待跟进",
        "回答人": [],
        "回复内容": "",
        "来自群聊": "用户反馈群",
        "是否命中知识库": ""
      }
    }
  ]
}
EOF
```

**Verify（写入后必做）**：
1. 用 `lark-cli base +record-list` 按时间/群聊过滤，确认**写入记录数 == `collected_count`**
2. 抽查记录：`一级分类`/`跟进状态` 枚举合法、`是否命中知识库` 满足规则、附件字段已关联
3. 发现缺漏或错误 → 修复字段后**重跑对应记录的写入**，再校验
4. 全部通过后，向用户简要报告写入成功与统计

### 12. 输出格式与校验
**输入**：全部处理结果
**输出**：严格 JSON（config_summary / window_summary / dimension_summary / collected_items）

输出必须为严格 JSON，不输出解释性段落。完整结构与字段规则见 `references/output-format.md`，校验清单见下节 Critical。
## Critical：强约束（输出校验 checklist）

> 以下约束必须逐项校验，任何违反均视为格式错误。**输出前必须逐项勾选通过**。

- [ ] **输出格式**：最终输出是一个且仅一个 JSON 对象，无 Markdown/表格/说明文字/代码块/列表/注释
- [ ] **顶层字段**：仅含 `config_summary` / `window_summary` / `dimension_summary` / `collected_items` 四个字段，不增删
- [ ] **配置信息**：`config_summary` 含全部配置信息（含 `classification_standard`），便于追溯重跑
- [ ] **记录字段**：`collected_items` 每项字段与用户配置的字段映射完全一致
- [ ] **空值处理**：无值字段保留并填空字符串 `""`、数字 `0`、布尔 `false` 或空数组 `[]`，不省略
- [ ] **分类约束**：`一级分类` 默认只允许 `技术问题`/`产品建议`/`使用咨询`/`待划定`；用户自定义分类时只允许用户定义的值；不得为空
- [ ] **跟进状态**：只允许 `待跟进`/`已完成`/`重复问题`；不得为空
- [ ] **回复一致性**：`待跟进`/`重复问题` 时 `回答人`/`回复内容` 为空字符串 `""`；`已完成` 时两者不得同时为空
- [ ] **知识库字段**：未提供知识库时 `是否命中知识库` 为空字符串 `""`；提供时仅 `技术问题`/`产品建议`/`使用咨询` 填 `是`/`否`，`待划定` 为空
- [ ] **待划定**：信息不足/上下文无法补足/知识库判断失败/无法稳定分类时，`一级分类` 必须为 `待划定`
- [ ] **统计一致**：`dimension_summary` 各计数之和 == `window_summary.collected_count` == `collected_items` 数量；`collected_count` ≤ `total_messages`；自定义分类时用用户分类作为键
- [ ] **图片处理**：`image_field_enabled`/`images_processed` 准确；图片字段按配置类型填写
- [ ] **字段数量**：`collected_items` 每项字段数量与用户配置一致

若任一约束不满足，先修正再输出，不得发送格式错误的 JSON。

## 重试机制

网络请求类操作（消息拉取、图片下载/上传、记录写入）遵循统一重试策略：

- **重试次数**：最多 3 次（首次失败后重试）
- **退避策略**：指数退避，重试间隔 1s → 2s → 4s（或 2s → 4s → 8s）
- **可重试的失败**：网络超时、HTTP 5xx、限流/速率限制（429）、瞬时连接失败
- **不重试直接失败**：权限不足（403）、参数错误（400/422）、资源不存在（404）
- **放弃条件**：3 次重试后仍失败 → 放弃该操作，记录错误信息，继续处理其他消息，不影响整体流程
- 图片上传失败且重试无效时：在对应记录图片字段填写错误描述（见 `references/image-processing-guide.md`）

## 耗时与超时

预估耗时（单日窗口、常规消息量）：

- **拉取 1 天消息**：约 10-30s（消息量大时更长，可分批 `--page-size 200` 拉取）
- **拉取大时间窗口（7 天+）**：可能 1-5 分钟，需分批并注意限流
- **图片下载**：约 2-5s/张；**图片上传**：约 5-15s/张
- **批量写入记录**：单次 batch 约 1-5s

超时处理：
- 单次 lark-cli 命令超时阈值建议 60s（可加长参数）；超时后按"重试机制"执行
- 整体流程超长时，及时向用户同步进度，不要静默长时间无响应
- 若某步持续失败（如权限不足），停止该步并向用户报告，不无限重试

## 使用模板

## 边界提醒

- 不要把公告、附和、纯闲聊塞进 `collected_items`
- 不要把"回复动作"误当问题
- 不要把"不会用"和"产品坏了"混成一类
- 不要默认要求用户粘贴消息内容，优先自动读取群聊
- 不要在本技能中做负责人分配、问题归并、生成知识条目
- 默认分类标准下产品建议需要录入反馈表；仅当用户分类标准不含产品建议分类时才过滤掉
- 用户未提供知识库时，不填充"是否命中知识库"字段
- 图片处理遵循用户配置的字段类型要求；确保图片上传成功后再关联到记录
- 二级分类根据具体问题类型填写，可为空字符串

## 常见问题处理

### Q: 如何处理群聊中的回复消息？
A: 回复消息需补充原始消息上下文。向前查看同线程消息，找到被回复的原始问题，将两者内容合并处理。

### Q: 图片上传失败怎么办？
A: 按"重试机制"最多重试 3 次；仍失败则在对应记录的图片字段填写错误描述，不影响其他字段处理。

### Q: 如何处理重复的反馈？
A: 与已有记录语义比对，判定重复则标记 `跟进状态` 为 `重复问题`，`回答人`/`回复内容` 填空字符串。

### Q: 用户自定义字段映射如何处理？
A: 按用户提供的字段映射关系，将标准字段映射到目标表格实际字段名，确保数据正确写入。
