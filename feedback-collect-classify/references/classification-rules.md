# 分类规则详解

## 概述

本文档详细说明 feedback-collect-classify 技能中的分类规则和判定标准。默认分类标准为四大分类（技术问题、产品建议、使用咨询、待划定）；用户提供具体分类时使用用户提供的分类标准。

## 四大分类定义（默认分类标准）

### 1. 技术问题 (Technical Issues)

#### 定义
本应可用，但实际异常、报错、失效、结果错误、卡死、白屏、兼容失败、数据丢失等问题。

#### 核心特征
- **预期行为**: 功能应该正常工作
- **实际行为**: 功能出现了异常或错误
- **本质**: 系统或功能的技术故障

#### 典型场景

**系统错误**
- 应用崩溃、闪退
- 白屏、黑屏
- 卡死、无响应
- 内存溢出、性能异常

**功能失效**
- 按钮点击无反应
- 功能无法正常使用
- 操作没有预期结果
- 数据保存失败

**报错信息**
- 明确的错误代码（如 0x80070057）
- 错误提示信息
- 异常堆栈信息
- API 调用失败（500、404等）

**数据问题**
- 数据丢失
- 数据显示错误
- 数据同步失败
- 数据格式异常

**兼容性问题**
- 特定系统版本不兼容
- 特定浏览器不支持
- 特定设备无法使用
- 版本升级后功能异常

#### 判定标准

**明确技术问题**
```
✅ "点击保存按钮后没有反应，也没有提示信息"
✅ "应用启动时就崩溃了，错误代码是 0x0000005"
✅ "导出功能报错，提示服务器内部错误"
✅ "数据同步一直失败，显示网络连接超时"
```

**边界情况**
```
⚠️ "这个功能不太好用" → 需要更多上下文，可能归为待划定
⚠️ "有时候能用，有时候不能用" → 需要具体复现步骤
```

#### 排除标准
```
❌ "不知道怎么用这个功能" → 使用咨询
❌ "希望能增加某个功能" → 产品建议
❌ "界面不太好看" → 产品建议
```

### 2. 产品建议 (Product Suggestions)

#### 定义
用户对产品功能、交互、体验等提出的新增/修改建议或期望。默认分类标准下纳入收集和分类，录入反馈表。

#### 核心特征
- **用户意图**: 期望产品新增、修改或优化某个能力
- **问题本质**: 表达诉求、建议或未来期望
- **解决方向**: 记录并转交产品团队评估

#### 典型场景
- "希望能支持批量导出功能"
- "建议增加深色模式"
- "这个交互可以更友好一些"
- "如果能支持某格式就更好了"

#### 判定标准

**明确产品建议**
```
✅ "建议增加导出PDF功能"
✅ "希望能支持深色模式"
✅ "交互体验可以优化一下"
```

**边界情况**
```
⚠️ "这个功能不太好用" → 需要更多上下文，可能归为待划定
⚠️ "要是能支持XX就好了" → 产品建议
```

#### 排除标准
```
❌ "点击保存没反应" → 技术问题
❌ "怎么导出数据" → 使用咨询
❌ "怎么申请权限" → 使用咨询
```

### 3. 使用咨询 (Usage Inquiries)

#### 定义
用户在问怎么用、当前能力边界是什么、权限怎么申请、收费怎么理解、入口在哪、规则是什么等问题。

#### 核心特征
- **用户意图**: 想要了解或使用某功能
- **问题本质**: 缺乏使用知识或信息
- **解决方向**: 提供使用指导或信息说明

#### 典型场景

**使用方法**
- "这个功能怎么用？"
- "如何进行数据导出？"
- "在哪里可以找到设置？"
- "操作步骤是什么？"

**能力边界**
- "系统支持哪些文件格式？"
- "最多可以添加多少个用户？"
- "这个功能有什么限制？"
- "是否支持批量操作？"

**权限申请**
- "如何申请管理员权限？"
- "普通用户能做什么操作？"
- "如何提升账号权限？"
- "权限被拒绝了怎么办？"

**收费理解**
- "这个功能需要付费吗？"
- "免费版和付费版有什么区别？"
- "如何购买套餐？"
- "费用是如何计算的？"

**入口位置**
- "在哪里可以下载？"
- "登录入口在哪里？"
- "如何访问某个页面？"
- "找不到某个按钮"

**规则说明**
- "这个功能的使用规则是什么？"
- "有什么注意事项？"
- "使用限制是什么？"
- "是否需要审核？"

#### 判定标准

**明确使用咨询**
```
✅ "如何申请管理员权限？"
✅ "数据导出功能在哪里？"
✅ "免费版有什么限制？"
✅ "系统支持哪些文件格式？"
```

**边界情况**
```
⚠️ "功能不太好用" → 需要更多上下文，可能归为待划定
⚠️ "总是提示错误" → 可能是技术问题，需要具体错误信息
```

#### 排除标准
```
❌ "点击保存没反应" → 技术问题
❌ "希望增加导出PDF功能" → 产品建议
❌ "界面太复杂了" → 产品建议
```

### 4. 待划定 (Pending Classification)

#### 定义
当前信息不足、语义含混、上下文补全后仍无法稳定归类，或内部置信度低于 70 的问题。

#### 核心特征
- **信息不足**: 缺乏关键信息
- **语义含混**: 表达不清晰或有歧义
- **置信度低**: 分类判断不稳定
- **需要人工**: 难以自动化处理

#### 典型场景

**信息不足**
- "有问题"
- "不行"
- "还是不行"
- "怎么处理"

**语义含混**
- "这个功能"
- "那个地方"
- "不太好"
- "有问题"

**依赖上下文但无法补全**
- 短消息且前文无法获取
- 回复消息但原始问题丢失
- 跨线程的引用

**置信度低于 70**
- 分类判断存在明显歧义
- 多个分类都有可能
- 缺乏关键判别信息

#### 判定标准

**明确待划定**
```
✅ "有问题"（无上下文）
✅ "还是不行"（无法补全上下文）
✅ "这个功能不太好"（语义含混）
✅ "怎么处理"（缺乏具体问题）
```

**上下文补全后的待划定**
```
⚠️ "还是不行" + context_summary: "用户A反馈某个功能有问题，但无法确定具体是哪个功能"
   → 归为待划定，需要人工确认
```

#### 处理策略

1. **优先补全上下文**: 尝试从前后文中获取更多信息
2. **置信度评估**: 对分类结果进行置信度评分
3. **低分处理**: 置信度 < 70 的统一归为待划定
4. **人工复核**: 标记为需要人工进一步分类

## 分类决策流程

### 决策树

```
开始
  ↓
是否有明确的报错或异常？
  ├─ 是 → 技术问题
  └─ 否 ↓
      是否在询问如何使用或相关信息？
        ├─ 是 → 使用咨询
        └─ 否 ↓
            是否在表达产品新增/修改建议或期望？
              ├─ 是 → 产品建议
              └─ 否 ↓
                  信息是否充足？
                    ├─ 是 → 待划定（语义含混）
                    └─ 否 ↓
                        置信度 >= 70？
                          ├─ 是 → 待划定（复杂情况）
                          └─ 否 → 待划定（信息不足）
```

### 关键问题

在分类时回答以下关键问题：

1. **是否涉及系统故障或错误？**
   - 是 → 技术问题
   - 否 → 继续判断

2. **是否在寻求使用指导或信息？**
   - 是 → 使用咨询
   - 否 → 继续判断

3. **是否在表达产品新增/修改建议或期望？**
   - 是 → 产品建议
   - 否 → 继续判断

4. **信息是否充足且表达清晰？**
   - 是 → 可能是待划定（复杂情况）
   - 否 → 待划定（信息不足）

5. **分类置信度是否 >= 70？**
   - 是 → 按分类结果处理
   - 否 → 待划定

## 置信度评估标准

### 90-100 分（信息明确，分类无明显歧义）

**特征**:
- 问题描述清晰完整
- 包含关键的技术细节或使用场景
- 分类判断毫无悬念

**示例**:
```
"点击保存按钮后没有反应，也没有提示信息，等待了30秒还是这样"
→ 技术问题，置信度: 95
```

### 80-89 分（有上下文支撑，分类较稳定）

**特征**:
- 有上下文信息支撑
- 问题描述基本完整
- 分类判断较为确定

**示例**:
```
"还是不行" + context_summary: "用户A反馈更新系统后出现错误代码0x80070057，用户C表示同样问题仍未解决"
→ 技术问题，置信度: 85
```

### 70-79 分（基本可判断，但有轻微歧义）

**特征**:
- 信息基本充足
- 存在轻微的分类歧义
- 需要一定的推断

**示例**:
```
"这个功能不太好使用"
→ 待划定，置信度: 75
（可能是使用咨询，也可能是产品建议）
```

### 60-69 分（信息不足，分类不稳定）

**特征**:
- 关键信息缺失
- 分类判断不稳定
- 需要更多信息确认

**示例**:
```
"有问题"
→ 待划定，置信度: 65
（完全不知道是什么问题）
```

### < 60 分（严重缺少信息，需要人工复核）

**特征**:
- 信息严重不足
- 无法进行有效分类
- 必须人工介入

**示例**:
```
"那个"
→ 待划定，置信度: 45
（完全无法理解）
```

## 特殊场景处理

### 产品建议

**定义**: 用户对产品功能、界面、体验等方面的改进建议或期望

**处理**: 默认分类标准下纳入收集和分类，录入反馈表；仅当用户提供的自定义分类标准不含产品建议分类时，才不录入反馈表并直接过滤掉

**示例**:
```
✅ "希望能增加暗黑模式" → 产品建议
✅ "建议简化操作流程" → 产品建议
✅ "界面可以更好看一些" → 产品建议
✅ "希望能支持批量导出" → 产品建议
```

### 重复反馈

**定义**: 与已有记录语义等价的反馈

**处理**: 标记为"重复问题"，不填写回答人和回复内容

**示例**:
```
已有��录: "网络连接频繁断开"
新反馈: "总是提示网络已断开"
→ 重复问题
```

### 混合反馈

**定义**: 一条反馈中包含多个问题

**处理**: 
- 主要问题决定分类
- 在 `反馈原文` 中保留完整内容
- 在 `standard_title` 中概括主要问题

**示例**:
```
反馈原文: "登录有问题，而且导出功能也用不了"
standard_title: "登录功能异常"
问题分类: 技术问题
```

### 情绪化反馈

**定义**: 包含强烈情绪表达的反馈

**处理**: 
- 提取核心问题，去除情绪化表达
- 在 `standard_title` 中使用客观表述
- 在 `反馈原文` 中保留原始内容

**示例**:
```
反馈原文: "这个破功能又坏了，烦死了！"
standard_title: "功能异常无法使用"
问题分类: 技术问题
```

## 分类质量控制

### 自动化验证

1. **枚举值验证**: 确保分类值在允许范围内
2. **字段一致性**: 验证相关字段的一致性
3. **置信度检查**: 低置信度自动归为待划定

### 人工审核

1. **定期抽样**: 对待划定问题进行人工审核
2. **边界案例**: 处理复杂的边界情况
3. **规则优化**: 根据审核结果优化分类规则

### 持续改进

1. **误判分析**: 分析分类错误的原因
2. **规则调整**: 根据分析结果调整规则
3. **模型训练**: 收集标注数据用于模型训练
